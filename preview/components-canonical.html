Border model, both themes (added 0.8.0 — Wave 2.1)

Three roles, not one generic "border": subtle — decorative separation only, the surface stays identifiable without it (used for row dividers, section rules). structural/control (--border-control, new) — necessary to recognize a control or panel boundary; derived from --text-primary rather than a fixed neutral so it remains ≥3:1 in Core and the sanctioned product surface fixture (used by form inputs). strong — emphasis/high-hierarchy separation, already ≥3:1 by construction. Not every border needs the same guarantee — see docs/tokens/semantic-borders-and-status.md.

`--destructive --compact --icon` (rightmost above) is technically supported, not blocked — shown here as a low-consequence example ("remove filter chip"). For a high-consequence/irreversible destructive action, prefer the default 44px density instead of compact, or require a confirmation step — a small unlabeled icon target is an easy mis-tap for something irreversible. Guidance, not a restriction.

DO — use icon-only for universally understood actions where space matters; always provide an accessible name via `aria-label`; compose canonical modifiers (`ac-button ac-button--{variant} [ac-button--compact] ac-button--icon`). DON'T — create a local `.table-action-button`/`.dashboard-icon-button` family; override width/padding locally to fake a square control; rely on a tooltip (`title`) as the accessible name; pair `--destructive` with `--compact --icon` for a high-consequence action without a confirmation step.
